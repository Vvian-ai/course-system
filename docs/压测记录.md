# 选课并发压测记录

| 项目 | 说明 |
| --- | --- |
| 应用 | Spring Boot 3.2.5，单实例，本机运行 |
| 数据库 | MySQL 8.0.46（本机） |

| 测试数据 | 200 个测试学生（T001 ~ T200）+ 1 门课程 TEST01（容量 50） |

## 测试方法

200 个并发线程，每个线程先从 CSV 读取一个学生账号登录，再调用选课接口。
每轮测试前清空 TEST01 的选课记录，保证从零开始。

```sql
DELETE FROM enrollment WHERE course_id = 'TEST01';
```

测试后统计实际选课人数：

```sql
SELECT COUNT(*) FROM enrollment WHERE course_id = 'TEST01';
```

## 逐轮观察

### 第 1 轮：基线（未加并发保护）

**结果**：容量 50 的课程，实际有 **51 人**选上，超出 1 人。

**现象分析**：

- 无重复选课记录，说明 `(student_id, course_id)` 唯一索引工作正常
- 选上的学生并非连续编号：T001 ~ T050 中缺少 T035，另外混入了 T073 和 T116
- 这个分布说明存在竞态窗口——请求的先后和抢到名额的顺序并不一致

**原因**：容量校验是「先查询当前人数，再插入记录」，两步之间存在时间差。
两个请求同时读到同一个计数时，都会判断为「未满」并执行插入，导致超出容量。

**结论**：容量校验存在 TOCTOU（检查后再使用）竞态，在并发场景下不可靠。
唯一索引只能防止同一学生重复选课，无法防止超额选课。

### 第 2 轮：基线（Ramp-up 调整为 0）

**结果**：容量 50 的课程，实际有 **52 人**选上，超出 2 人。

**现象分析**：

- 相比第 1 轮的 51 人略有增加，说明请求越集中，被利用的竞态窗口越多
- 选上的学生分布更分散：T001 ~ T052 中有 8 个学号未入选，
  同时还混入了 T073、T088、T110，甚至排在名单最后的 T200 也抢到了名额
- 依然没有重复选课记录

**观察**：超卖幅度没有随并发集中度显著上升，可能与数据库连接池有关。
HikariCP 默认最大连接数为 10，同一时刻真正并行执行 SQL 的请求数量有限，
其余请求进入等待队列——连接池在客观上压低了并发程度。

**结论**：两轮基线（51 人、52 人）均复现超卖，容量校验的竞态问题得到确认。

### 第 3 轮：加入悲观锁（与第 1 轮同参数对比）

**修复方式**：在 `CourseRepository` 中增加带 `@Lock(LockModeType.PESSIMISTIC_WRITE)` 的查询方法，
选课时通过它读取课程记录，等价于 `SELECT ... FOR UPDATE`，把同一门课的并发选课请求串行化。

**结果**：容量 50 的课程，实际 **50 人**选上，**没有超卖**。

**对比第 1 轮**（同为 200 并发、Ramp-up 1 秒）：

| 指标 | 第 1 轮（无保护） | 第 3 轮（悲观锁） |
| --- | --- | --- |
| 实际选课人数 | 51 | 50 |
| 是否超出容量 | 是（超出 1 人） | 否 |

**结论**：悲观锁有效。同一组并发参数下，容量校验的竞态被消除。
代价是同一门课的选课请求从并行变为排队执行，吞吐量会下降——这是为保证数据正确性付出的成本。

### 第 4 轮：悲观锁 + 请求同时到达（暴露更深层的问题）

**结果**：容量 50 的课程，实际有 **59 人**选上，超出 9 人——比没有加锁的基线还严重。

**排查过程**：

1. 确认代码改动已生效：`CourseRepository` 中有 `@Lock(LockModeType.PESSIMISTIC_WRITE)` 的查询，
   `CourseService.selectCourse` 使用的是 `findByIdForUpdate`
2. 确认数据库隔离级别：`SELECT @@transaction_isolation` 返回 **REPEATABLE-READ**

**原因**：MySQL 默认的 REPEATABLE-READ 隔离级别下，事务在**第一次读取数据时会建立一个快照**，
之后事务内所有的普通 SELECT 都从这个快照读取，即使其他事务已经提交了新数据。

而 `selectCourse` 的执行顺序是：

```java
List<Enrollment> existing = enrollRepo.findByStudentId(studentId);  // 第一条查询，快照在此建立
...
Course course = courseRepo.findByIdForUpdate(courseId);            // 加锁（锁定读，读到的是最新数据）
long enrolled = enrollRepo.countByCourseId(courseId);              // 普通查询，读的仍是旧快照
```

所以：**悲观锁确实把请求排成了队，但每个事务数出来的人数仍然是它进入事务那一刻的数字。**
锁保护了写入的顺序，却保护不到快照读——排在后面的事务拿到的依然是过期的人数。

这也解释了为什么第 3 轮（Ramp-up 1 秒）恰好是 50 人：请求分散时，
各事务的快照时间比较接近真实值，侥幸没有超卖；一旦请求真正同时到达（Ramp-up 0），
问题就暴露了。

**结论**：只加悲观锁不足以保证正确性，还必须让容量校验读到最新数据。

### 第 5 轮：悲观锁 + READ_COMMITTED（与第 4 轮同参数对比）

**修复方式**：将 `CourseService.selectCourse` 的事务隔离级别显式设为 `READ_COMMITTED`：

```java
@Transactional(isolation = Isolation.READ_COMMITTED)
public Enrollment selectCourse(String studentId, String courseId) { ... }
```

**结果**：容量 50 的课程，实际 **50 人**选上，**没有超卖**。

**对比第 4 轮**（同为 200 并发、Ramp-up 0）：

| 指标 | 第 4 轮 | 第 5 轮 |
| --- | --- | --- |
| 事务隔离级别 | REPEATABLE-READ（默认） | READ_COMMITTED |
| 实际选课人数 | 59（超出 9 人） | 50 |
| 是否超出容量 | 是 | 否 |

**结论**：诊断成立。悲观锁本身没有问题，问题在于 REPEATABLE-READ 下事务内的普通 SELECT
读取的是事务开始时的快照，使容量判断基于过期数据。改为 READ_COMMITTED 后，
每条查询都读取最新已提交数据，配合行锁即可正确拦截。

## 结论汇总

四组参数、五种配置的对照结果：

| 并发保护 | Ramp-up 1 秒 | Ramp-up 0 秒 |
| --- | --- | --- |
| 无保护 | 51 人（超 1）❌ | 52 人（超 2）❌ |
| 悲观锁 | 50 人 ✅（见下方说明） | 59 人（超 9）❌ |
| 悲观锁 + READ_COMMITTED | 未测（0 秒已通过，1 秒条件更宽松） | **50 人 ✅** |

说明：第 3 轮（悲观锁 + Ramp-up 1 秒）得到 50 人，看似已经解决，
但第 4 轮换到请求同时到达的条件后立刻暴露问题——**这说明轮次设计很重要，
只在宽松条件下验证容易得出错误结论**。

## 经验总结

1. **「先查询、再写入」的容量校验在并发下必然不可靠**，必须让检查与写入具备原子性
2. **唯一索引只能防止同一主体重复提交，无法防止总量超限**，两者是不同层面的保护
3. **加锁不一定够**：锁保证了执行顺序，但如果判断依据来自事务快照，锁也救不了
4. **验证要覆盖最严苛的条件**：宽松条件下的通过可能只是时序侥幸
5. 可选的进一步优化：改为「条件更新」（`UPDATE ... WHERE enrolled_count < capacity`），
   用一条原子语句同时完成检查与扣减，比悲观锁少一次查询、锁持有时间更短
